# 公众号发文

把一份内容源变成公众号后台草稿箱里排好版、配好图的一篇文章。

读者是**公众号上的普通读者**（教育同行、家长、同事），不是内部同事——文章里
不能出现只有项目内部才懂的说法，也不能出现真实的学校名和人名。

约定两件事：①下文「用户」指操作这套流程的人（通常是写文章的顾问本人），
检查点问的就是这个人；②本流程只负责**从内容源到草稿箱**，内容源本身怎么来
（诊断怎么做的、工作坊怎么跑的）不在这里。

## 需要同目录安装的兄弟包

本流程自己不画图、不排版，四件事分别交给同目录的兄弟包。安装时它们必须和
本包**放在同一个 skills 目录下**，本文里的相对路径才成立：

| 兄弟包 | 干什么 | 本流程在哪一步用 |
|---|---|---|
| [`../ian-illustrations/SKILL.md`](../ian-illustrations/SKILL.md) | 正文叙事插画（顾问 IP「Ian」，16:9 横版二次元） | Phase 3 图线 A |
| [`../guizang-material-illustration/SKILL.md`](../guizang-material-illustration/SKILL.md) | 封面主视觉、知识图解类插画（归藏 3D 编辑风） | Phase 3 图线 B / 可选图线 D |
| [`../guizang-social-card-skill/SKILL.md`](../guizang-social-card-skill/SKILL.md) | 公众号封面套图版式（21:9 主封面 + 1:1 方封面，网页渲染出图） | Phase 3 图线 C |
| [`../wechat-draft-publisher/SKILL.md`](../wechat-draft-publisher/SKILL.md) | 排版成公众号样式 + 推草稿箱 | Phase 4 |

缺哪个就在对应环节走该环节写明的降级路径，不要拿别的包硬顶——各家的画风和
尺寸口径不通用。

若内容源是用 `../diagnosis-report/` 出的诊断报告，直接拿它的白话版报告当输入；
没有那个包也不影响，任何形态的内容源都能走这条流程。

## 边界（先说清不管什么）

- **只到草稿箱，不发布**。即使用户说「帮我发出去」，也只做到草稿，然后告诉他
  去后台自己点发布。理由：群发是不可撤回的对外动作，且公众号每天群发次数有限，
  这个决定必须由人做。这条与 `../wechat-draft-publisher/` 的边界一致。
- **不做小红书、不做视频号**：竖版卡片图文走 `../xhs-post/`（若已安装）。
- **不替用户凭空构思内容**。什么都没给、只说「写篇公众号」→ 反问：这篇要讲哪件
  事、素材在哪（报告/记录/笔记都行）、给谁看。没有内容源就不开工。
- **不改内容源的判断**。文章是把已有判断讲给公众听，不是在文章里重新下判断；
  内容源里被弃权、没证据的部分，文章里也不许补成结论。

## 工作区约定

所有中间产物落在当前项目的 `.local/<文章代号>/` 下。**真实材料与未匿名化的稿子
一个字节都不许进 git**——开工前先确认当前项目的 `.gitignore` 里有 `.local/`；
没有就先加，或者改用用户指定的仓库外目录。

```
.local/<文章代号>/
├── source/            # 内容源（报告/记录/笔记）原件，只读、不删——写文章时要回来核细节
├── article.md         # 文章素材：标题候选 + 正文（含【图N】占位）+ 配图清单 ★正文与图位的唯一出处
├── prompts/           # 每张图一份提示词文件 p1.txt、p2.txt…（重生成时改这里，不改记忆里的）
├── images/            # 正文插画成品
│   └── v1/            # 重生成前的旧版挪到这里留档，不删
├── covers/            # 封面主视觉 + 封面套图（网页文件与渲染出的图）
└── DELIVERY.md        # 交付说明（发布前给用户看的那份，见 Phase 4）
```

**article.md 是正文与图位的唯一出处**：正文改了段落、加减了图，必须顺一遍
配图清单里的图号和插入位置——图号漂了，正文和图就会对错位（Phase 3 的成品
验收里有这一项）。旧图**归档不删**：换回去的成本比重生成低得多。

## 工作流总览

```
Phase 1  校准（读 IP 设定本体 + 封面规格本体 + 消化内容源）
   ▼
Phase 2  写文章（匿名化正文 + 3 个标题候选）+ 配图规划（shot list + 封面方案）
         + 列生图通道候选
   ▼
[Checkpoint 素材]  ← 必须停。一次攒批对齐：文章 / 标题 / 配图规划 / 走哪个生图通道
   ▼
Phase 3  出图（正文插画 → 封面主视觉 → 封面套图 →〔可选〕知识图解）
         每出一张当场质检，不合格立刻重生成
   ▼
[Checkpoint 成品]  ← 必须停。图文一起给用户验收
   ▼
[Checkpoint 推稿]  ← 必须停。推草稿前确认标题/署名/摘要/封面
   ▼
Phase 4  排版推草稿箱 + 交付说明（含 AI 标识告知）
```

为什么只停这三处：**通道拍板前停**（可能要花用户的钱）、**成品出来停**
（图文对不对味只有人能判）、**推稿前停**（推进后台的东西改起来麻烦，标题署名
摘要一次说清）。中间的写作、生图、质检不逐条打扰用户。

## Phase 1 —— 校准

动手写之前，先把三件容易记错的事**读原件确认**，不采信任何二手转述（包括本文件
里的描述、其他文档里的路由说明、上一次会话的印象）：

1. **顾问 IP 的当前设定** —— 打开 [`../ian-illustrations/references/ian-ip.md`](../ian-illustrations/references/ian-ip.md)
   与该包的 `SKILL.md`、`references/style-dna.md` 读一遍。
   **这是 IP 设定的唯一出处。**
   ⚠️ 已知有过时引用在流传：`../wechat-draft-publisher/SKILL.md` 的「准备封面」
   一节里还写着一个叫 `ian-xiaohei-illustrations` 的旧包（旧 IP「小黑」，黑色实心
   身体的形象）——**那是过时的，不要用**。碰到任何文档说「配图用小黑」，一律以
   `../ian-illustrations/` 的实际内容为准。（2026-08 实跑翻过这个车：先照旧引用
   找到了小黑设定，被用户当场打断纠正。）
2. **封面规格的当前要求** —— 打开 [`../wechat-draft-publisher/SKILL.md`](../wechat-draft-publisher/SKILL.md)
   的「准备封面」一节，看它当前要的比例和尺寸；再看 `scripts/md2wx.mjs` 的
   `--cover` 参数说明，确认**它一次只收一张封面图**。封面怎么排在 Phase 3 图线 C，
   但**尺寸口径以这里读到的为准**，不以本文件或社交卡包里的默认值为准。
3. **内容源** —— 通读一遍，落到 `.local/<文章代号>/source/`（只读、不删）。
   提炼：这篇文章要讲的那**一件事**是什么、有哪些能公开讲的现场细节、
   哪些是内容源里明确弃权/没证据的（那些不许写进文章）。

## Phase 2 —— 写文章 + 配图规划 + 列通道

### 2.1 文章

按 [`templates/article-material.md`](templates/article-material.md) 的骨架写进
`article.md`。写之前重读 `references/CRAFT.md` §文章写法与 §匿名化。

要点（细则在 CRAFT）：3 个标题候选不替用户定；顾问第一人称；从一个具体现场
细节开场；真实校名人名一律换角色代称；结尾给三个能直接拿去用的动作；正文里
用 `【图1】`…`【图N】` 标出配图位置。

### 2.2 配图规划

四条图线，按内容需要取用（**每条都要说清为什么要这张图**，凑数的图不做）：

| 图线 | 做什么 | 交给谁 | 规格 |
|---|---|---|---|
| A 正文叙事插画 | 正文里的认知锚点（判断、循环、前后对比、角色状态） | `../ian-illustrations/` | 16:9 横版，一般 4~8 张，短文 1~3 张 |
| B 封面主视觉 | 一张能当封面用的主图 | `../guizang-material-illustration/` | 按 Phase 1 读到的封面比例 |
| C 封面套图 | 把主视觉排成公众号封面版式 | `../guizang-social-card-skill/` | 21:9 主封面 + 1:1 方封面 |
| D 知识图解（可选） | 正文里需要"讲清结构"的地方（流程、层级、对比数据） | `../guizang-material-illustration/` | 随正文，横版 |

shot list 每张写清六件：**放哪一段之后 / 主题 / 这张图要说的核心意思 / 结构类型 /
IP 在图里做什么动作 / 建议的中文标注词**（格式见 `../ian-illustrations/SKILL.md`
第 2 步）。规划**只写内容与结构，不写具体画风参数**——画风归各兄弟包的设定文件
管，在这里写死等于把生图环节降级成翻译机，而且画风一改这里就漂。

### 2.3 列生图通道候选

生图是本流程唯一**可能花用户钱**的环节，按外部依赖契约办，见下节。此时只做一件事：
**探测当前环境里实际可用的通道，列成候选清单带到检查点**，不要自己选、更不要
自己开通。

## 生图通道契约（外部依赖）

本流程对生图通道只有三个要求：**能按提示词出图 / 能指定画幅比例 / 能把图落到
本地文件**。满足这三条的通道都能用，换通道只改本节和 `prompts/` 里的调用方式，
文章和 shot list 不动。

**候选清单现场探测，不硬编码**——环境里有什么就列什么。2026-08 实跑时遇到过的
三类，供识别参考：

| 通道类型 | 识别方式 | 费用与前置 |
|---|---|---|
| 会话内置的生图能力 | 当前环境直接能调 | 通常不额外花钱，优先探测 |
| 本机装的生图命令行工具 | 装了但要密钥/接入点/账号 | **花用户自己的账号额度**；可能还要先开通资源 |
| 只出提示词、不出图 | 永远可用 | 零成本兜底 |

给用户的候选清单必须逐条写清三件事：**这个通道要不要花钱 / 有没有前置动作
（配密钥、开资源）/ 出来的图能不能保住指定画风**。

同时**给 2~3 个带理由的推荐**（"推荐 X，因为它不花钱又能出 16:9"），用户说
「你定」→ 取推荐里的第一个，**明说选了哪个、为什么、花不花钱**，给他反悔的机会。

### 花钱这条线（红线）

**任何会产生费用或开通付费资源的动作，必须用户明确点头之后才做。** 包括但不限于：
开通/创建计费资源（如新建一个按量计费的生图接入点）、切换到按调用收费的通道、
批量重生成。

- 用户说「用 X 通道」= 同意用这个通道出图，**不等于**同意为它开通新的付费资源。
  发现还要先开通，**回去再问一次**，说清"要先开一个按量计费的资源，开了之后
  生成和后续调用都按用量扣你的账"，等他答应再动手。
  （2026-08 实跑：要建接入点前停下来问，用户回了「go」才建。）
- 无法与用户交互的环境（被当作一次性任务调用）：**一律降级到「只出提示词」**，
  把提示词写好落盘，停在这里交人，不得自行开通任何资源。

### 降级底线

一张图都生不出来时，**不阻塞整篇文章**：把每张图的完整提示词写进 `prompts/`，
文章正文照常交付，`DELIVERY.md` 里写明"图还没生成，提示词在这里，你在任何能
生图的地方跑一下就有"。文章和草稿箱那步不依赖图能不能生出来（正文可以先不放图，
但**封面是必需的**——微信没封面创建不了图文，这时要请用户给一张现成图当封面）。

## Checkpoint 素材（**硬节点**）

文章和配图规划写完必须停，一次攒批对齐（全白话，不提文件路径以外的技术词）：

```
文章和配图方案出来了，请你一次定几件事：

1. 标题挑一个（也可以让我按你的意思改）：
   ① <标题候选 1>
   ② <标题候选 2>
   ③ <标题候选 3>
2. 正文：<一句话说清这篇怎么讲的>，全文在 <article.md 路径>。
   里面所有学校名和人名都换成了角色（校长/中层/某位老师），你要实名再告诉我。
3. 配图打算做 <N> 张：<每张一行：第几张 · 画什么 · 放在哪段之后>；
   封面另外做一张主视觉 + 一套公众号封面（大图 + 方图）。
4. 画图走哪条路，你定一下：
   ① <路子 A> —— <要不要花钱 / 要先弄什么>
   ② <路子 B> —— <同上>
   ③ 我只把每张图的画法写清楚、不出图 —— 不花钱，你之后自己在别处跑
   我的建议是 <推荐项 + 一句话理由>。你说「你定」我就按这个走。

定完我就开始画，中间不再一张张来问你。
```

**没对齐前不许进 Phase 3**：图画完再改文章框架，等于图全部重做。
无法与用户交互的环境：把待定项写进 `article.md` 顶部，停在此处交人，
**不得自行挑通道、更不得开通任何要花钱的东西**。

## Phase 3 —— 出图

顺序：先正文插画（图线 A）→ 再封面主视觉（B）→ 再封面套图（C）→ 可选知识图解（D）。
先做正文插画的理由：它张数最多、最容易暴露画风与文字问题，问题在这里暴露比在
封面上暴露便宜。

### 每张图的固定动作

1. **写提示词**：写之前重读 `references/CRAFT.md` §图上文字硬规则；按对应兄弟包
   的提示词模板写，落到 `prompts/pN.txt`（改图改这个文件，不凭记忆重写）。
2. **生成**：用检查点上定的通道，一张一张出，不要把多张拼成一张。
3. **当场质检**：图一出来就对着 `references/CHECKLISTS.md` §A 逐项过，
   **不要等全部生成完再统一看**——早一张发现，后面几张的提示词就能一起改对。
4. **不合格立刻重生成**：改 `prompts/pN.txt` 里对应的约束再跑；**旧图挪进
   `images/v1/`，不删**。

**看不了图的环境怎么办**（当前环境打不开图片文件）：第 3 步的质检自己做不了，
**不许跳过、也不许假装看过**。降级：把 `references/CHECKLISTS.md` §A 的清单
原样附进 Checkpoint 成品的汇报里，请用户对着清单看一眼（重点是前四条：人名、
英文、标注字数、编造的数字），并在 `DELIVERY.md` 里写明"图这次是你自己看的，
我没能打开"。

### 图线 C 封面套图的两个坑

- **规格以发布端为准**：`../guizang-social-card-skill/` 默认出 21:9（2100×900）
  主封面 + 1:1（1080×1080）方封面，而 `../wechat-draft-publisher/` 一次只收
  **一张**封面图。所以：**主封面那张进推稿命令，方封面作为文件交付给用户，
  由他在后台草稿里自己换/裁**。推稿前按 Phase 1 读到的当前比例要求核一遍两边
  对不对得上，对不上以发布端为准重排。
  ⚠️ 这条对应关系在 2026-08 实跑中**没有跑到推草稿那一步**（实跑止于封面渲染），
  首次真跑请核实实际效果，并把结果记进 `FIELD-NOTES.md`。
- **它要浏览器渲染**：这个包用网页排版再截图出图，需要装 Playwright 和一个
  浏览器内核（体积大）。装不上时的降级：**跳过套图**，直接把图线 B 的封面主视觉
  按发布端要求的比例出一张当封面用，并在交付说明里写明"方封面这次没做"。

## Checkpoint 成品（**硬节点**）

图全部到位后必须停，图文一起交用户验收：

```
文章和图都齐了。

标题：<定稿标题>
正文：<article.md 路径>（<N> 处配图位置都对上了）
配图：<逐张：第几张 · 画的什么 · 放在哪段之后 · 文件路径>
封面：主封面 <路径>；方封面 <路径>〔或：这次没做，原因…〕

几点说明：
- 图里没有出现任何真实人名、学校名，也没有英文字样。
- 〔如有〕图上带着平台自动加的 AI 生成标识，很淡，在右下角。按现在的规定，
  AI 生成的内容本来就要带这类标识，发出去保留即可。要不带标识的版本我另想办法。
- 〔如有〕第 <N> 张重做过一版，旧版留在 <v1 路径> 里，想换回去随时说。

你看看：哪张要重画、哪段要改、标题要不要换。都可以的话我就去排版推草稿。
```

用户提修改 → 只改被指出的那一层（文字问题改正文、画面问题改提示词重生成、
位置问题改配图清单），**不整篇重做**。改完重新确认。
无法与用户交互的环境：把上面这段写进 `DELIVERY.md`，停在此处交人，不要自己
放行进推稿。

## Checkpoint 推稿（**硬节点**）

推草稿前最后一停，把要写进公众号后台的四样东西一次确认清楚：

```
准备推到草稿箱了，确认四样：
1. 标题：<定稿标题>
2. 署名：<作者名>（公众号后台显示的那个署名，你要用哪个？）
3. 摘要：<一句话摘要>（留空的话微信会自动取正文前 54 字）
4. 封面：<用哪张>

推完它就静静躺在你后台的草稿箱里，**我不会发出去**——发布那一下你自己在
后台点。确认了我就推。
```

**无法与用户交互的环境：一律不推**。把标题/署名/摘要/封面的建议值写进
`DELIVERY.md`，连同排好的稿子和图一起交人，由人来跑最后这一步——推进后台的
东西撤起来麻烦，这个动作不值得替用户做。

## Phase 4 —— 排版推草稿 + 交付说明

1. 交付前先过 `references/CHECKLISTS.md` §C（**含隐私扫描**：正文和图里
   还有没有漏网的真实校名人名），逐项写结论，**fail 先修再推**。
2. 按 `../wechat-draft-publisher/SKILL.md` 走：先跑它的自检确认链路是通的
   （第一次用要配公众号的凭据、可能要加 IP 白名单，它的文档里写了怎么弄），
   再 `convert` 出预览看排版，最后 `publish` 推草稿。
   - **正文里不要放外部链接**——微信会把它们变成不能点的纯文字。要给链接就用
     「阅读原文」那一个位置。
   - 推完拿到回执后，告诉用户去后台草稿箱看，重点确认两件事：**封面缩略图在不在、
     正文里的图显示不显示**。
   - 这个包不可用时的降级（凭据配不上/网络不通/没装 Node）：把排好的 Markdown
     和全部图片打包交给用户，说明"这些直接贴进公众号后台编辑器就行，图要一张张
     传"，流程照常收尾。
3. 写 `DELIVERY.md` 交付说明，固定覆盖五项：
   - 草稿在哪（后台草稿箱，标题是什么）
   - **发布这一下由你点**（我没发，也不会发）
   - 图有几张、各放在哪
   - **AI 标识**：图上有没有平台自动加的 AI 生成标识，有就如实写明位置和处理建议
   - 还没做/没跑通的部分（如方封面没做、某张图没生成只有提示词）

## 交付与验收

把草稿链接/回执 + `DELIVERY.md` 交给用户，直接问：

> 按你自己的标准，这篇能发吗？哪儿不行？

不合格时先定位是哪一层再改最小的那一块：**文字层**（正文/标题 → 改 article.md）、
**画面层**（图 → 改 prompts 重生成）、**版式层**（排版/封面 → 重排或换封面）。
不要整篇重做——重做会把已经对的部分改坏。

## 出了问题怎么办

用这套流程翻了车（图画歪了、稿子不像人写的、草稿推不上去、读者反馈不对味），
把案例记进 [`FIELD-NOTES.md`](FIELD-NOTES.md)。翻车不是流程失败，是它变强的原料。
