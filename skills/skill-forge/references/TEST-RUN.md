# TEST-RUN —— 真实案例试跑协议（Phase 3）

skill 的真实用户是**未来的陌生会话**。本协议保证交付前，skill 至少被
"陌生人"用真实案例完整跑通过一次。三条原则（真实案例 / 冷启动 /
验收活儿不验收文本）见 SKILL.md Phase 3，此处是执行细则。

---

## 1. 要案例

向用户要一个**真实业务案例**：最近真做过的、或正要做的一单活，连同
真实输入材料。话术示例（业务语言）：

> 你的操作手册写好了，交付前要拿真活儿验一次。给我一单你们最近做过
> （或正要做）的活的原始材料——就像平时把活儿交给新人那样给我。
> 做过的更好：有你们自己的成品可以对照。

按可得性取用，只往下走不跳级：

1. **做过的案例** → 最优。跑完可拿旧成品当参照（产出不必和旧成品一样
   才算合格，验收仍以用户现场判断为准）。
2. **要做的案例** → 可用。产出直接是有用的活，用户验收动力最足。
3. **口述场景** → 用户拿不出材料时，让用户口述一个真实场景的细节
   （何时 / 谁 / 什么材料 / 期望产出），由口述落成输入材料。
4. **准真实输入** → 这活儿确实还没人干过、口述也无从谈起时，用"用户
   手上最接近的东西"代替：半成品、同行/竞品的公开案例、类似场景的
   材料。用它跑出的结论按"未验收交付"处理（见 §5）。
5. **禁止 agent 自己编案例**——编的案例会顺着 skill 的假设走，暴露
   不了盲区。1~4 全不可得时直接走 §5 的未验收交付，不造假案例硬跑。

## 2. 冷启动执行（按能力降级，只往下降不往上跳）

### ① 独立冷跑（最优）

条件：能起一个**不继承本会话上下文**的执行体——独立 agent / subagent，
或新进程、新窗口、另一个 AI 工具（能起新进程时优先新进程，隔离最彻底）。

给它的输入**只有三样**：skill 包路径、案例输入材料、一句开场指令
（"按 <skill 路径> 的流程处理 <案例材料>"）。**不给访谈记录、不给设计
过程、不做任何口头补充**——补充了就不是冷跑。

冷跑中它停下来提问时，**先分类再处置**，这是本档的关键纪律：

| 提问类型 | 处置 |
|---|---|
| a) 案例事实问题（材料里有的信息） | 照答，只答材料范围内的事实 |
| b) skill 文本歧义（"这步是什么意思"） | **不解释**，原样记录为 skill 缺陷——skill 理解不了 = skill 要改 |
| c) 检查点决策问题（口味 / 方向 / 取舍，产出 skill 的硬检查点会正常触发这类提问） | **原样转交真实用户**，由用户答；主持试跑的 agent 一个字不代答——代答 = 拿访谈记忆污染冷跑，是最隐蔽的自欺 |

**能力前提**：本档要求独立执行体的提问能回传、用户的回答能送达。
环境做不到（如 subagent 一次性跑完无法中途交互）且产出 skill 带硬
检查点 → 本档不可用，**降档②**。

### ② 用户新会话冷跑（首选兜底——用户本人就是天然的冷上下文）

只要用户在场愿意配合，就用这档，**优先于档③**。代价只是一次复制粘贴，
换来真正的隔离。给用户一段现成指令：

> 请打开一个全新的对话，把下面这段原样发出去：
> 「按 <skill 路径 / 或把这些文件发给它> 的流程，帮我处理这单活：
> <案例材料>」。中途它问你什么，你就按平时的想法答。跑完把产出
> （和你觉得别扭的地方）发回给我。

顺带收集：中途它问了什么、哪里卡住、用户觉得哪里别扭——都是修复输入。
检查点决策天然由用户亲自答，无污染问题。

### ③ 同会话冷读（末档，仅当用户明确不配合档②时用）

同一会话的上下文已被访谈污染，自律靠不住——本档的防线不是自我约束，
而是**可核查的出处追溯**：

1. 若访谈记录已落盘（工作区的 INTERVIEW-NOTES.md，见 SKILL.md 工作区
   约定），立规矩：**本轮禁止打开它**。
2. 从头重读 skill 包全部文件后开跑。产出中**每一条领域判断旁标注依据**：
   `〔依据：SKILL.md §X / CRAFT.md 第 N 条 / 案例材料〕`。标不出来的
   照写产出，但标 `〔无出处〕`。
3. 跑完机械导出两份清单：「有出处项」/「无出处项」。**无出处清单原样
   交给用户看**——用户不懂 skill 结构，但一眼能认出"这条讲究我跟它
   说过，可手册里好像没写"。判定权交给用户，不留在写 skill 的 agent
   手里。
4. 无出处清单非空 → 逐条补进 skill（补得进 CRAFT.md 的补 CRAFT.md，
   属流程的补流程）→ 再验产出。

本档天花板仍低于①②。用了③，交付汇报必须注明"试跑为同会话冷读"，
并建议用户把上线首单当第二次试跑对待。

## 3. 验收

把试跑产出交给用户，问法（业务语言，验收活儿不验收文本）：

> 这是按新手册跑出来的活儿。按你们平时的标准：合格吗？不合格的话，
> 具体哪里不行？

不许问"skill 写得怎么样"。用户只说得出"感觉不太行"时，用对照法追问：
拿他自己认可过的成品（或 §1 的参照案例）并排摆开，请他指"这两份差在
哪几处"——把感觉翻译成位置。

## 4. 修复循环

用户判不合格（或冷跑过程暴露缺陷）→ **先定位问题层，再修**：

| 症状 | 问题层 | 修法 |
|---|---|---|
| 产出内容外行 / 不对味 / 老手一眼假 | craft 层 | 回 Phase 1 补访谈：拿着不合格产出问用户"差在哪"，把答案翻成新原则补进 CRAFT.md |
| 流程走岔 / 中间产物对不上 / 该停没停 / 重复环节越做越走样 | harness 层 | 回 Phase 2 查 MECHANISMS.md：这是哪类失败模式，配什么机制 |
| 冷跑 agent 理解偏了 / 卡住提问 / 引用不出条文 | 表述层 | 直接改 skill 文本消歧义 |

四条纪律：

1. **禁止表面缝补**——产出错一处就在 skill 里加一句"注意别错这处"，
   是把设计缺陷当防坑条款；层没定位对，同类错误换个地方还会出。
2. **每修必重跑**：任何一层修完都重新冷跑（可只重跑受影响环节，但
   受影响环节必须冷跑）。
3. **每个坑登记产出 skill 的 FIELD-NOTES.md**：症状 / 定位的层 / 修法 /
   日期。这是防坑条款唯一合法的出生地（红线 5）。
4. **三轮收敛出口**：同一类问题修到第 3 轮仍不合格 → 停止继续修，
   改做**范围收缩**——把最不收敛的那段从 skill 的自动流程里砍掉，二选一：
   ①明确写进"本 skill 不管什么"的边界；②把该环节改成硬检查点，产出
   交人判断后再继续。然后带已知限制清单交付。无限打磨会耗尽用户耐心，
   且 skill 越修越厚——收窄范围的可靠 skill，好过全能但不可靠的。

循环出口：用户判"合格"（或触发三轮收敛出口）。此时把访谈阶段标注
"待试跑验证"的推演失败模式过一遍——试跑中真出现过的转正（去掉标记），
没出现的保留标记留给线上迭代观察，**不因为没出现就删**（一单试跑的
覆盖有限）。

## 5. 未验收交付（唯一合法的免试跑出口）

仅当 §1 的 1~4 档案例来源全部不可得（典型：这活儿还没人干过、也无
任何相近材料）时启用：

- 交付状态明确标注为**"未验收交付"**，交付说明里写清（业务语言）：
  > 这份手册还没用真活儿验过。你第一次真用它，就是它的首次试跑——
  > 跑完不管好坏，把结果带回来，按结果修一轮，它才算真正交付。
- skill 的 FIELD-NOTES.md 头部登记"未验收"状态与原因，首单真实使用
  后按 §4 走一遍修复循环再转正。
- 本出口不适用于"用户嫌麻烦不想给案例"——那种情况按 §1 话术再争取，
  案例可得而不用就是违反红线 6。
