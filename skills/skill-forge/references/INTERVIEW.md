# INTERVIEW —— 萃取访谈手册

目标：把用户脑子里（和语料里）的领域经验，翻译成四张产物——领域画像 /
失败模式清单 / 验收标准 / craft 原则表。用户全程只说业务语言。

**总纪律**（凌驾于一切问题设计）：

1. 问题里零工程黑话（红线 3）。问坑、问讲究、问好坏——不问机制、流程节点、
   检查点。
2. 用户答不上来 → 换案例角度再问一次 → 还不行就记空缺，**不许编内容填坑**
   （红线 2）。
3. 每拿到一个关键回答，即时用一句业务语言复述确认（"你的意思是……对吧"），
   别攒到最后一次性对——那时用户已经忘了自己说过什么。
4. 有语料先读语料。访谈只补语料的盲区，重点补 craft 层（手册通常不写讲究）
   和翻车案例（手册通常只写正确做法）。**读不了的格式**（PDF / PPT /
   截图 / 在线文档，当前环境打不开时）→ 请用户导出成文本或把关键章节
   粘贴过来；实在拿不到就走全访谈，并在 BLUEPRINT.md 标注"语料未消化"
   ——不许假装读过。
5. 访谈过程中把用户原话随手记进工作区 `INTERVIEW-NOTES.md`（craft 溯源
   的证据库），访谈收尾把四张产物按 `templates/BLUEPRINT-TEMPLATE.md`
   落盘成 `BLUEPRINT.md`。

## 路径 A —— 开放式访谈（懂行业务方）

特征：用户张口就是流程、角色、坑。让他多说，你负责追问和翻译。
一轮可以问 4~6 个问题，通常 1~2 轮出货。

### 问题库（按产物分组，每组挑用、按对话自然衔接，不逐条机械问）

**① 领域画像**

- 这活儿从头到尾是怎么干的？从接到需求到交出去，走几步？
- 每一步交出来的东西是什么？（文档？数字？一个决定？）
- 哪几步有先后依赖——前一步没定，后一步就白干？
- 干这活儿平时用什么工具 / 材料 / 数据？

**② 失败模式**

- 这活儿交给一个聪明但没经验的新人，他最可能搞砸的三个地方是什么？
- 你见过的最典型的翻车长什么样？当时是怎么发现的？
- 哪一步做错了最伤、返工最贵？哪些错无所谓、顺手就能改？
- 有没有那种"表面看着对、其实坏了"的错？怎么识破的？

**③ 验收标准**

- 你怎么一眼看出一份产出是外行做的？
- 一份合格的产出，你验收时看哪几个地方？
- 什么情况下你会直接说"重做"？
- 有没有做得特别好的案例？好在哪？（有实物就要来当语料）

**④ craft 层**

- 有没有那种规矩上没写、但老手都知道的讲究？
- 新人问"为什么要这么做"时，你怎么解释的那些道理？
- 这行里有没有你们内部才懂的黑话 / 分寸感？（比如"这个度要拿捏"——
  拿捏的到底是什么？）
- 同样一份活，老手和新手的产出摆在一起，差距具体差在哪？

### 追问技法

- **要案例不要概念**：用户说"要注意分寸" → 追问"举一个没把握住分寸的
  真实例子"。概念翻译不成原则，案例才能。
- **要判据不要形容词**：用户说"要专业" → 追问"专业和不专业的两份产出
  摆一起，你指给我看差在哪一行"。
- **返工成本必须问到**：每个失败模式都要标高/中/低——它直接决定后面
  在哪设停下来确认的节点。

## 路径 B —— 选项引导式访谈（业务小白）

特征：用户有意图但说不清流程。开放题会把他问僵，必须给选项、给场景。
纪律：**每轮 ≤3 问，每问给 2~4 个具体选项 + "都不是，我说说"兜底**。
通常 3~4 轮，节奏慢是正常的。

### 轮次骨架

**第 1 轮 —— 圈边界**

- 这个 skill 帮你干的活，最像下面哪种？〔列 3~4 个该领域的典型任务形态〕
- 干完这活儿，你手里多出来的东西是什么？〔一篇文字 / 一张表 / 一个方案 /
  一个决定〕
- 这活儿现在是谁在干？〔你自己 / 你团队 / 外包 / 还没人干过〕

**第 2 轮 —— 挖坑（用场景不用抽象）**

- 假设明天来了个新人干这活儿，你最不放心哪件事？〔按第 1 轮答案生成
  3 个具体场景选项〕
- 上次这活儿干得不顺利，是卡在哪？〔选项 + 兜底〕

**第 3 轮 —— 定好坏**

- 下面两种说法，哪种更接近你判断活儿好坏的方式？〔用第 1、2 轮信息
  构造两个具体对比场景〕
- 如果只能提一个要求，产出必须做到什么你才收货？

**第 4 轮（如需）—— 补 craft**

- 把你以前满意过的一份成品发我看看？（把 craft 萃取从"问"改成"从实物里
  抄"——小白往往说不出讲究，但拿得出好东西）
- 没有自己的成品（第 1 轮答了"还没人干过"）→ 退而求其次："你见过的、
  觉得'要是我们也能做成这样就好了'的例子？别人家的也行。"从范本里
  抄 craft，溯源标注"用户认可的外部范本"。连范本都没有 → craft 层
  如实留薄，**不许编造凑数**；在 Blueprint 对齐时明说"讲究这块目前是
  空的，第一单试跑后从你的反馈里补"——这类 skill 大概率走 TEST-RUN §5
  的未验收交付，提前给用户打好预期。

### 路径 B 特别纪律

- 小白的失败模式清单会偏薄，**agent 推演项的占比会更高**——推演项必须
  全部标"待试跑验证"，且 Phase 3 试跑轮次预期更多，提前告知用户。
- 小白给的验收标准往往是"我看着舒服"。这不是废话，把它落成
  "Phase 3 由用户亲自看产出拍板"的验收方式，不要硬逼他给量化标准。

## 翻译方法：回答 → 四张产物

访谈是原料，翻译才是产出。规则：

| 用户说的 | 翻成 | 落到 |
|---|---|---|
| "先……然后……最后……" | 阶段 + 依赖关系 | 领域画像 |
| "新人老是……" / "上次翻车是……" | 失败模式（症状 + 触发场景 + 返工成本） | 失败模式清单 |
| "我一看……就知道不行" | 验收判据（保留原话） | 验收标准 |
| "这个要拿捏 / 有讲究 / 老手才懂" + 案例 | craft 原则（一条原则 = 一句话判断 + 溯源） | craft 原则表 |

**agent 特有死法的推演**（失败模式清单的第二来源，翻译完用户口述后做）：

拿着领域画像，逐阶段问自己四个问题：

1. 有没有同一信息要出现在多处产物里？→ 漂移风险
2. 有没有环节会重复 N 次？→ 长会话遗忘风险
3. 有没有环节需要克制（照做就行，别发挥）或需要发挥（别机械翻译）？
   → 过度发挥 / 翻译机风险
4. 有没有一次性向用户倾倒大量信息或问题的点？→ 决策淹没风险

推演出的条目**单独分组、标"待试跑验证"**，在 Checkpoint Blueprint 里
也如实告诉用户"这几条是我按 AI 的常见毛病预判的，跑一单就知道真假"。
