# MECHANISMS —— 失败模式 → 机制 适应症表

skill-forge 的核心资产。Phase 2.1 拿失败模式清单**逐条查表**：
症状匹配适应症 → 确认禁忌症不成立 → 确认降级路径可用 → 选入，
并登记进「机制 ↔ 失败模式映射表」。

**使用方向是"失败模式找机制"，不是"把机制用全"。** 一个简单领域的
skill 只用 3 个机制是好事。除标注〔底座件〕的两条外，任何机制若在
映射表里找不到对应失败模式，就是红线 1 违规。

每条五栏：**适应症** / **禁忌症** / **降级**（只会读 markdown + 写文件的
agent 怎么执行）/ **写法要点** / **出处**（本表自身遵守红线 2：每条机制
溯源到真实 skill 的真实实践；标"推演"的条目 = 尚无直接案例，待产出
skill 的试跑验证）。出处里 "wvp" = web-video-presentation，一个经受过
真实使用检验的成熟 skill，本表首版主要蒸馏自它。

---

## M1 分阶段流水线

- **适应症**：任务有天然先后依赖；后段建立在前段产物上，前段错了后段白干。
- **禁忌症**：单步任务；探索型任务（顺序本身就该由过程决定）。
- **降级**：天然支持——就是 markdown 章节顺序。
- **写法要点**：每阶段写清「进入条件 / 产出物 / 下一步」。阶段划分跟随
  领域画像里人干活的真实分段，不要为了好看强造阶段。
- **出处**：wvp 的 Phase 1→4 主干。

## M2 硬检查点（攒批对齐）

- **适应症**：存在只有用户能拿的决策（口味 / 方向 / 资源投入），且集中在
  某时点前后；零碎问会打断用户，也会诱导 agent 自作主张。
- **禁忌症**：决策 agent 自己能定（有客观判据）；用户明确要求全自动。
- **降级**：天然支持——"此处必须停，按以下模板汇报，等用户回复再继续"。
- **写法要点**：①一个检查点攒一批决策一次对齐，别设一串小检查点；
  ②配汇报模板（M10）；③写清"没对齐前不许进入下一阶段"；④检查点位置
  由失败模式的**返工成本**决定——设在"做错了最伤"的环节之前；⑤给面向
  小白的 skill 配"分批确认"变体（一次 ≤3 项），防决策淹没；⑥选项类决策
  按 M15 的交互协议出题。
- **出处**：wvp 的 Checkpoint Plan（"5 件事一次对齐"）；⑤为推演（对应
  小白画像的决策淹没风险，待验证）。

## M3 锚点先行再扇出

- **适应症**：产出物含 N 个同构单元（章节 / 条目 / 页面 / 批次），且指引
  可能有盲区——第 1 个单元做完先验收，盲区在最便宜的时机暴露，后续单元
  以它为样板。
- **禁忌症**：单元间无共性可复用。
- **降级**：天然支持——"第 1 个单元做完必须停下验收，通过后再做其余"。
- **写法要点**：写明锚点验收看什么（从验收标准里抽）；写明后续单元
  "参考锚点的什么"（模式 / 骨架）与"不必对齐什么"（避免机械复制）。
- **出处**：wvp 的"第 1 章 = 主线程 + 强制验收，早改成本最低"。

## M4 唯一真相源

- **适应症**：同一信息出现在多处产物里、且存在**人工同步动作**——
  凡靠"记得改这边也改那边"维持一致的，必然漂移。
- **禁忌症**：信息只有单一去处。
- **降级**：天然支持——"以 X 为唯一标准；改动 X 后按以下清单逐处核对"。
- **写法要点**：指名哪个文件/字段是真相源；列出全部下游位置；写清
  改动后的同步动作。若环境能跑脚本，可附一致性检查脚本作为增强。
- **出处**：wvp 的 narrations.ts（"保证 5 处地方永远不会漂"）。

## M5 单一入口必读文件

- **适应症**：某个子任务会重复 N 次，且每次都要遵守同一套原则——长会话
  里 agent 第 3 次做时就开始凭记忆走样。
- **禁忌症**：一次性任务；原则少到两三行（直接内联进流程即可）。
- **降级**：天然支持——"每次做 X 之前，重新读一遍 Y.md，不许凭记忆"。
- **写法要点**：入口必须**单一**——该环节的所有原则并进一份文件，不要让
  agent 每次拼装三四个文件；产出 skill 的 CRAFT.md 通常就设在重复次数
  最多的环节上。
- **出处**：wvp 的 CHAPTER-CRAFT.md（"写章节时只读一份"，Part 0~8 并为
  单一入口）。

## M6 自检协议 + 修复铁律

- **适应症**：产出有客观清单可查的部分（字段齐不齐、规则守没守、该问的
  问没问）。
- **禁忌症**：仅限**质量判据**部分——好坏纯靠主观品味时不设质量清单
  （交给 M11 用户验收），但形式完整性清单照设。
- **降级**：降级链写进 skill——①能开独立 agent 就让它拿清单逐项核查并
  汇报 pass/fail + 证据；②不能就自己逐项过、每项写一行结论。两档共用
  铁律：**先按 fail 项修完，再汇报 / 再推进**。
- **写法要点**：清单来自访谈的验收标准，不是 agent 编的通用质量条款；
  "逐项写结论"必须写死，防目测放行。
- **出处**：wvp 的"硬性自检协议"（三级降级 + "直接拿原始结论汇报但
  不修复 = 违规"）。

## M7 规划 / 执行留白

- **适应症**：流程里有创造性环节，上游规划写太细会把下游执行变成翻译机，
  产出千篇一律。
- **禁忌症**：下游就该机械执行（合规操作 / 数据处理）——这时反着用：
  写死每一步，禁止发挥。
- **降级**：天然支持——给规划产物写"必须写 / 禁止写"双列表。
- **写法要点**：双列表要具体到字段级；同时在执行环节给决策依据
  （craft 层），留白不是放养。
- **出处**：wvp 的"outline 不写动画"（写死动画 = chapter agent 退化为
  翻译机）。

## M8 派工契约（并行 / 顺序两用）

- **适应症**：同构单元可物理隔离（各自的文件 / 目录 / 命名空间互不相碰）。
- **禁忌症**：单元间强耦合改不开。
- **降级**：无并行能力时**降级为顺序模式，而不是简化契约**——契约原文
  变成"顺序做每个单元前的自我简报"：开工前把契约各项逐项过一遍再动手。
- **写法要点**：契约必须自包含五件套：①本单元的规划段落；②单一必读
  文件路径（M5）；③锚点样板的参考方式（M3）；④物理隔离硬规则（各写
  各的文件、不碰共享文件）；⑤完工验证动作。并行版补预期管理：单元间
  风格有差异是预期，由公共约束兜底。**执行档位做成用户选项**（逐个确认 /
  顺序批量 / 并行），并写明"用户中途可切换档位"。
- **出处**：wvp 的模式 C（subagent prompt 五要素 + 每章独立 CSS 前缀 +
  不碰 chapters.ts）及模式 A/B/C 用户选档 + "随时可中途切换"。

## M9 输入分诊表

- **适应症**：用户可能带不同形态的输入进场（有材料 / 没材料 / 半成品 /
  只有想法），不同形态起点不同。
- **禁忌症**：输入形态唯一。
- **降级**：天然支持。
- **写法要点**：一张两列表——"用户给的东西 → 该做的"；必含一行
  "什么都没给 → 反问要什么"，写清 skill 不替用户凭空构思的边界。
- **出处**：wvp 的 1.1 识别用户输入表（含"啥都没有 → 反问"行）。

## M10 汇报模板〔底座件〕

- **性质**：无禁忌症，凡有检查点 / 交付时刻就默认配备；映射表里记
  "底座"，不占失败模式行。
- **降级**：天然支持。
- **写法要点**：模板是骨架不是填空题答案——固定"必须覆盖的项"，内容
  按实际情况填；面向用户的模板全程业务语言（红线 3）。
- **出处**：wvp 的 Checkpoint 总结模板 / 第 1 章验收模板。

## M11 真实案例验收〔底座件〕

- **性质**：无禁忌症，产出好坏最终由人的业务判断说了算——这是 M6
  管不了的部分的兜底，默认配备；映射表里记"底座"。
- **降级**：天然支持——"把产出交给用户，问：按你们的标准，这活儿合格吗"。
- **写法要点**：验收对象是**活儿**不是过程文档；不合格时先定位问题层
  再修（craft 层 / 流程层 / 表述层），不做表面缝补（M19）；面向小白的
  skill 加追问技法：说不出"哪里不行"时，拿他自己认可过的成品并排对照
  逐处指认。
- **出处**：wvp 第 1 章验收清单（用户看效果拍板）；小白追问技法为推演
  （对应"小白只会说'感觉不太行'"，待验证）。

## M12 防坑条款

- **适应症**：**已经真实翻过的车**——试跑或线上使用中暴露的具体坑。
- **禁忌症**：想象出来的坑（红线 5）。没证据的"可能会……"是噪音，
  会稀释真条款的权威性。
- **降级**：天然支持。
- **写法要点**：每条带案发记录（何时 / 什么症状 / 怎么修的），统一登记
  在产出 skill 的 FIELD-NOTES.md；SKILL.md 正文只在对应环节加一行指引。
  条款随迭代协议生长。
- **出处**：wvp 的"bump STORAGE_KEY"（踩过才写）。

## M13 脚手架 / 模板

- **适应症**：产出有稳定重复的文件结构或文档骨架。
- **禁忌症**：产出结构每次都不同。
- **降级**：能跑脚本 → 脚手架脚本；不能 → "按以下目录 / 骨架手动创建"
  清单 + 模板文件。**规格以降级版为准**，脚本只是加速器（红线 4）。
- **写法要点**：模板里可留占位符 + "这里该放什么"的指引注释，并写明
  成品里必须清零占位符。
- **出处**：wvp 的 scaffold.sh + themes/（配置数据化，不硬编码）。

## M14 双源原则（原始语料保留 + 下游回源取细节）

- **适应症**：流程是"原始材料 → 转写/提炼 → 再加工"的多级转写——每级
  转写都在压扁信息，末端产出会变干变薄（合同摘要、病历转写、客服工单
  提炼等垂类常见形态）。
- **禁忌症**：无原始材料（内容凭空创作）；单级转写且下游不再加工。
- **降级**：天然支持——"原始材料落盘不删；下游环节必须回原始材料抽
  细节，不许只依赖上一级的提炼产物"。可配"信息池"做法：转写时按单元
  预抽原文细节（数字 / 引用 / 案例）供下游直接取用。
- **写法要点**：写死两件事：①原始材料是只读的、不许删（在工作区约定
  M16 里标注）；②哪些环节必须回源、回源取什么。与 M4 是互补关系：
  M4 收敛（多处写一处），M14 发散（下游取数不许断根）。
- **出处**：wvp 的双源原则（原则 10："script 定节拍，article 定画面密度"）
  + "article.md 不删！" + 章节信息池。

## M15 带理由推荐 + "你定"兜底（选项类决策交互协议）

- **适应症**：检查点里有选项类决策（选风格 / 选方案 / 选模式），而用户
  可能不敢选、不会选、或直接说"你定"。
- **禁忌症**：决策有客观判据（那就不该问用户，agent 直接定，见 M2 禁忌症）。
- **降级**：天然支持。
- **写法要点**：三段式写死：①选项动态从数据/现状里取，不硬编码清单；
  ②agent 必须主动给 2~3 个**带理由的推荐**（"推荐 X 因为它匹配你说
  的……"）；③用户说"你定" → 取推荐第 1 个，**明说选了什么、为什么，
  给反悔机会**，并把代定项打标记，验收时优先复核。
- **出处**：wvp 的主题选择协议（动态读 theme.json 不硬编码 + bestFor
  匹配推荐 + "用户说'主题你帮我选'→取推荐第 1 个并告知原因"）。

## M16 工作区约定

- **适应症**：流程产生多个过程产物 / 中间文件，agent 若随手放，后续环节
  找不到、迭代时对不上。
- **禁忌症**：全程单文件产出。
- **降级**：天然支持——一张目录树 + 每个文件一句"是什么 / 谁写 / 谁读 /
  能不能删"。
- **写法要点**：目录树写进 SKILL.md 靠前位置；必须保留的文件（尤其
  M14 的原始材料、M4 的真相源）显式标注"不删"；工作区建在用户当前
  目录下、命名可预期。
- **出处**：wvp 的 `my-video/` 工作目录约定（含 "article.md 不删！"）。

## M17 外部依赖契约

- **适应症**：skill 依赖可替换的外部系统（数据库 / 通知渠道 / 生成服务 /
  行业工具），不同用户手里的实现不同。
- **禁忌症**：依赖唯一且不可替换。
- **降级**：契约本身就是 markdown——定义"实现方必须提供的最小接口"
  （几个动作、各自输入输出），内置 1~2 个参考实现的操作说明，另附常见
  替代品的现成接入片段。
- **写法要点**：契约最小化（两三个动作足矣）；写清"换实现只动哪个文件 /
  哪节"；红线 4 口径下，契约的降级底线是"由用户手动执行该动作并把结果
  贴回来"。
- **出处**：wvp 的 tts-providers（三函数契约 + 内置 2 实现 + 5 段现成
  替换片段）。

## M18 反模式清单（一眼假清单）

- **适应症**：该领域存在"外行做的一眼就露馅"的典型特征，且正面原则
  说不尽——负面清单比正面原则更易执行（逐条对照排除即可）。
- **禁忌症**：访谈/语料里挖不出真实的反面特征（不许编造凑数，红线 2）。
- **降级**：天然支持。
- **写法要点**：落在 CRAFT.md 的"一眼假清单"节；每条特征带溯源；在
  产出环节的完工自检（M6）里加一条"对照一眼假清单逐条排除"。
- **出处**：wvp 的反 AI 味反模式（Part 5：紫粉渐变 / 假插画 / emoji 等
  逐条排除）。

## M19 反馈分层速查

- **适应症**：产出 skill 交付后，用户会提修改意见——没有分层指引时
  agent 会整体重做，既慢又把对的部分改坏。
- **禁忌症**：几乎没有（凡有用户反馈环节都适用；产出一次性用完即弃的
  skill 可省）。
- **降级**：天然支持。
- **写法要点**：一张"反馈症状 → 所属层 → 最小修改动作"速查表写进产出
  skill；铁律：**先定位层，再改最小切片，不整体重做**。层的划分跟随
  该 skill 的实际结构（如：内容层 / 流程层 / 表述层）。
- **出处**：wvp 的 Part 8 反馈速查（"先定位是哪一层，再改最小切片，
  不要重做整章"）。

## 机制 ↔ 失败模式映射表（产出格式）

Phase 2.1 的产出物，最终作为附录写进产出 skill 的 SKILL.md：

```
| 失败模式（业务语言） | 返工成本 | 来源 | 机制 | 落点 |
|---|---|---|---|---|
| <症状描述> | 高/中/低 | 用户口述 / 语料 / 推演(待验证) | M2 硬检查点 | SKILL.md Checkpoint X |
| ——（底座件不占失败模式行） | —— | 底座 | M10 / M11 | <落点> |
| <症状描述> | ... | ... | 暂无机制，试跑观察 | —— |
```

两条硬规则：

1. 除底座件（M10 / M11）外，每个入选机制在表里至少占一行有真实失败
   模式的行（否则红线 1 违规，删机制）。
2. 每个"高返工成本"的失败模式必须有机制或明确写"暂无机制，试跑观察"
   ——不允许静默漏配。

## 本表的迭代

本表不是封闭清单：产出 skill 的试跑 / 线上翻车中若出现现有机制盖不住
的失败模式类型，把新机制（五栏齐全，出处指向那次真实案例）增补进来，
并在本包根目录 FIELD-NOTES.md 登记案发记录。表中标"推演"的写法要点，
被试跑验证后把标记转正。
