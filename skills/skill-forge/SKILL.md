# Skill Forge

把一位领域专家的经验，变成一份**未来的陌生 agent 会话拿起来就能稳定干活**
的垂类 skill。用户全程只说业务语言；失败模式分析、harness 机制选型、
skill 组装、试跑验证，全部由本 skill 负责。

## 核心方法论：失败模式驱动

一个优秀的垂类 skill，强不在"有检查点、有自检、有流程图"这些**形式**，
而在**每一个机制都对着一个真实的失败模式**——某个状态会漂移，所以要唯一
真相源；某条原则长会话会忘，所以要单一入口必读文件；某一步返工最贵，所以
要在它前面设硬检查点。

因此 skill-forge 的一切产出都遵循这条因果链：

```
业务语言访谈 → 失败模式清单 → 查适应症表选机制 → 组装 skill → 真实案例跑通
     ▲                                                        │
     └────────────── 跑不过 = 失败模式清单漏了，回炉 ──────────┘
```

**机制是失败模式的函数。** 没有失败模式支撑的机制，一律不许写进产出的
skill——先有坑，才有防坑的栏杆；反着来就是货物崇拜。

## 六条红线（贯穿全程，凌驾一切）

| # | 红线 | 一句话 |
|---|---|---|
| 1 | **无主机制** | 产出 skill 里任何机制答不出"防的是什么失败模式" → 删 |
| 2 | **现编 craft** | 领域原则每条必须溯源到用户原话或用户语料；agent 自己补的"看起来像原则的通用废话" → 删，或回访谈找用户确认 |
| 3 | **工程黑话** | 一切面向最终用户的文本（访谈问题 / 检查点汇报 / 交付说明）零工程黑话——不出现 harness / SSOT / subagent / 降级链这类词 |
| 4 | **能力假设** | 产出 skill 中任何一步依赖「读 markdown + 写文件」之外的能力，必须原地写明降级路径，否则不许写 |
| 5 | **想象防坑** | 没有真实翻车证据的防坑条款不许写。v1 skill 的防坑条款少是正常的，它们靠试跑和后续迭代长出来 |
| 6 | **未试跑交付** | 没用真实案例跑过 Phase 3 的 skill，不许说"交付"。唯一例外：案例确实不可得时走 TEST-RUN.md §5 的「未验收交付」——必须显式标注状态并约定首单真实使用即首次试跑 |

## 工作流总览

```
Phase 0   分诊
   0.1  判断用户画像（懂行业务方 / 业务小白）—— 从对话判断，不发问卷
   0.2  盘点已有语料（SOP / 培训材料 / 优秀与翻车案例）—— 有语料优先抄语料
   ▼
Phase 1   萃取访谈（业务语言 → 四张产物）
   1.1  领域画像：这活儿人是怎么干的
   1.2  失败模式清单：新手会怎么搞砸 + agent 特有的死法
   1.3  验收标准：什么算合格、什么算废品（用户原话）
   1.4  craft 萃取：规矩上没写、老手都懂的讲究
   ▼
[Checkpoint Blueprint]   ← 硬节点。用业务语言一次对齐 4 件事：
                           失败模式清单 / 流程骨架 / 验收标准 / 领域原则表
   ▼
Phase 2   组装 skill 包
   2.1  查适应症表：每个失败模式配机制，写「机制 ↔ 失败模式」映射表
   2.2  写 SKILL.md + references/（craft 层单独成文件）
   2.3  红线扫描（六条逐条过）+ 自检
   ▼
Phase 3   真实案例试跑（**硬节点，不可跳过**）
   3.1  向用户要一个真实业务案例
   3.2  冷启动跑新 skill（按能力降级选执行方式）
   3.3  用户按业务标准验收**活儿**（不是验收 skill 文本）
   ▼
[修复循环]   跑不过 → 定位问题层 → 回炉 → 再跑，直到用户判"合格"
   ▼
Phase 4   交付 + 迭代协议
```

## 工作区约定（过程产物必须落盘）

skill-forge 的过程产物**不许悬在会话上下文里**——长流程跑到 Phase 3
修复循环时，没落盘的失败模式清单和"待验证"标记早漂了。在用户当前
目录下建工作区：

```
<业务名>-forge/
├── INTERVIEW-NOTES.md   # 访谈原话记录（craft 溯源的证据库；档③冷读时禁止打开）
├── BLUEPRINT.md         # 四张产物落盘（按 templates/BLUEPRINT-TEMPLATE.md）
│                        #   Phase 2 逐条查表、Phase 3 修复循环、Phase 4 交付汇报都读它
├── 〔用户语料〕          # 用户给的手册 / SOP / 案例，原样保留不删（下游回源取细节）
└── <skill-name>/        # Phase 2 起组装的 skill 包本体
```

BLUEPRINT.md 是本流程的唯一真相源：访谈后写入，Checkpoint Blueprint
按它汇报，用户反馈改它，Phase 2.1 查表读它，试跑后"待验证"标记的
转正 / 保留也改它。

## Phase 0 —— 分诊

### 0.1 用户画像（从对话判断，不发问卷）

| 信号 | 判定 | 访谈路径 |
|---|---|---|
| 用户张口就是流程、角色、坑、案例 | 懂行业务方 | 开放式访谈（INTERVIEW.md 路径 A） |
| 用户说不清流程，只有模糊意图（"帮我做个写文案的 skill"） | 业务小白 | 选项引导式访谈（INTERVIEW.md 路径 B）：每轮 ≤3 问，给具体选项不给开放题 |
| 介于两者之间 / 判断不了 | 先按路径 A 问一轮，答不动立刻切路径 B | —— |

判定是动态的：访谈中途发现判错了，随时切换路径，不用告知用户。

### 0.2 已有语料盘点

开场必问（用业务语言）：

> 你们有没有现成的东西——操作手册、培训材料、SOP、做得特别好的案例、
> 翻过车的案例？有的话发给我，比访谈快得多，也准得多。

**有语料优先抄语料**：语料当骨架，访谈只补语料覆盖不到的隐性知识
（尤其 1.4 的 craft 层——手册里通常不写"讲究"）。没语料才走全访谈。

### 0.3 输入分诊表

| 用户给的东西 | 该做的 |
|---|---|
| 明确领域 + 有语料 | 读完语料 → 缩短版访谈（只补盲区）→ Checkpoint Blueprint |
| 明确领域 + 无语料 | 完整访谈（按画像选路径 A/B） |
| 只有模糊意图（"做个 XX 的 skill"） | 先用 2~3 个业务问题把领域边界问清（这个 skill 管到哪、不管哪），再进访谈 |
| 想改造 / 升级一个已有 skill | 读旧 skill → 按 MECHANISMS.md 逐机制问"这防的是什么坑" → 答不出的标记 → 走缩短版流程（访谈只针对标记项和新增需求） |

## Phase 1 —— 萃取访谈

详细问题库与执行方式见 [`references/INTERVIEW.md`](references/INTERVIEW.md)。
此处只钉住产物与纪律。

**四张产物**（访谈结束时必须齐）：

1. **领域画像**：这活儿人是怎么干的——步骤、先后依赖、每步产出什么。
2. **失败模式清单**：每条 = 症状 + 触发场景 + 返工成本（高/中/低）。
   两个来源缺一不可：①用户讲的"人会怎么搞砸"；②agent 视角推演的
   "agent 特有死法"（状态漂移 / 长会话遗忘 / 过度发挥 / 一次性倾倒信息），
   推演项必须标注"待试跑验证"，不与用户口述项混排。
3. **验收标准**：用户判断合格/废品的具体依据，尽量保留原话。
4. **craft 原则表**：规矩上没写、老手都懂的讲究。每条带溯源（用户原话
   引用或语料出处）——这是红线 2 的执行前提。

四张产物**必须落盘**到工作区 `BLUEPRINT.md`（按
`templates/BLUEPRINT-TEMPLATE.md` 的字段），访谈原话同步记进
`INTERVIEW-NOTES.md`——溯源抽查和档③冷读隔离都靠这两个文件。

**访谈纪律**：

- 所有问题都是业务问题。问"新人最容易搞砸在哪"，不问"你要什么检查点"。
- 翻译工作全部自己做：用户的回答翻成失败模式 / 验收标准 / 原则，
  **翻译结果用业务语言复述给用户确认**，确认动作放在 Checkpoint Blueprint。
- 用户答不上来的问题，换个案例角度再问一次；还答不上就记为空缺，
  **不许自己编内容填坑**（红线 2）。

## Checkpoint Blueprint —— 一次对齐 4 件事（**硬节点**）

访谈产物齐了之后必须停下来。用**业务语言**（红线 3）向用户汇报，
一次对齐 4 件事。汇报骨架：

```
访谈内容我整理完了，正式动手之前，请你确认 4 件事：

1. 【这活儿的坑】我理解容易搞砸的地方是这几个：
     - <失败模式 1，业务语言描述> （搞砸了返工代价：高/中/低）
     - <失败模式 2 ...>
   有漏的、说错的吗？

2. 【干活的顺序】skill 会按这个流程带着 AI 干活：
     <流程骨架，业务语言，标出会停下来找用户确认的节点>
   停下来确认的时机对吗？有该停没停、或不必停的吗？

3. 【好坏的标准】我记下的合格标准：
     - <验收标准，尽量用户原话>
   按这个判，行吗？

4. 【行家的讲究】我提炼的门道：
     - <craft 原则 1（出处：你说的"……"/ 某材料）>
   哪条不对、哪条漏了？

确认或修改后，我就开始做你们的这份「AI 操作手册」。
```

三条执行规则：

- **小白变体**：Phase 0 判为小白的用户，不一次抛 4 件事——拆成 2~3 批
  （先对坑和顺序，再对标准和讲究），每项给「对 / 不对 / 我说不好」
  三选一，"我说不好"的项按下一条处理。
- **用户说"你定"**：agent 取自己的推荐（推荐必须带理由），**明说选了
  什么、为什么，给反悔机会**；所有代定项在 BLUEPRINT.md 里打
  〔代定〕标记，Phase 3 试跑后优先复核这些项。
- **收尾**：收到反馈 → 改 BLUEPRINT.md → 改动大的（增删失败模式 /
  推翻流程骨架）再确认一轮；只是措辞级修正的，改完即进 Phase 2。
  **4 件事得到用户明确确认（或明确"你定"）之前，不许写 skill 本体。**

## Phase 2 —— 组装 skill 包

### 2.1 机制选型

打开 [`references/MECHANISMS.md`](references/MECHANISMS.md) 的适应症表，
**拿 BLUEPRINT.md 的失败模式清单逐条查表**：每个失败模式 → 选机制
（或明确"暂无机制，靠试跑观察"）。产出一张**机制 ↔ 失败模式映射表**
——它是这个 skill 的设计图纸，最终作为附录写进产出 skill，迭代时
照着改。

选型纪律：

- 方向是"失败模式找机制"，**不是**"把机制清单全用一遍"。一个简单领域的
  skill 可能只需要 3 个机制，这是好事不是偷懒。底座件（M10 汇报模板 /
  M11 真实案例验收）默认配备、不需失败模式支撑，映射表里记"底座"。
- 每选一个机制，同步确认它的禁忌症不成立、降级路径可用（红线 4）。

### 2.2 写 skill 包

按 [`references/PACKAGE-SPEC.md`](references/PACKAGE-SPEC.md) 的规格 +
`templates/` 的产出模板（SKILL / CRAFT / FIELD-NOTES 三份）组装。要点：

- craft 原则表落成 `references/CRAFT.md`——产出 skill 中重复次数最多的
  环节，把它设为"每次必读"单一入口。
- 产出 skill 的语言跟随用户的业务语言。
- 防坑条款区（FIELD-NOTES.md）v1 几乎为空是**预期状态**（红线 5）。

### 2.3 红线扫描 + 自检

按 [`references/CHECKLISTS.md`](references/CHECKLISTS.md) 逐条过六条红线
+ 组装完整性清单。

**执行方式（按能力降级，优先更隔离的方式）**：

1. 能开独立 agent / subagent → 让它拿"skill 包路径 + CHECKLISTS.md"逐项
   核查，严格汇报 pass/fail + 证据。
2. 不能 → 自己逐项过，每项写一行结论，不允许目测一遍放行。

**铁律：先按 fail 项修完，再进 Phase 3。**

## Phase 3 —— 真实案例试跑（**硬节点，不可跳过**）

详细协议见 [`references/TEST-RUN.md`](references/TEST-RUN.md)。此处钉住
三条不可妥协的原则：

1. **必须真实案例**。向用户要一个真实业务案例（最近真做过或正要做的活）。
   造的例子会顺着 skill 的假设走，暴露不了盲区。案例来源按 TEST-RUN.md
   §1 的四档取用（做过的 → 要做的 → 口述 → 准真实输入）；四档全不可得
   （这活儿还没人干过）→ 走 §5「未验收交付」，**永远不许 agent 编案例**。
2. **必须冷启动**。skill 的真实用户是未来的陌生会话；写 skill 的会话满脑子
   访谈上下文，自己跑自己的 skill 永远能跑通——那是作弊。执行方式按能力
   降级（详见 TEST-RUN.md §2，含各档关键纪律）：
   - ① 独立冷跑（独立 agent / 新进程），冷跑中的提问**先分类再处置**：
     事实照答 / 歧义记缺陷 / **检查点决策原样转交真实用户，不许代答**；
     提问无法回传用户且产出 skill 带硬检查点 → 本档不可用，降②；
   - ② 用户自己开全新会话跑（首选兜底——用户本人就是天然的冷上下文）；
   - ③ 末档：同会话冷读，防线是**出处追溯**——产出每条领域判断标注依据
     条文，无出处清单原样交用户核认，判定权不留在写 skill 的 agent 手里。
3. **验收活儿，不验收文本**。跑完把产出交给用户，问的是
   "这活儿按你们的标准，合格吗？哪里不合格？"——不是"skill 写得行吗"。
   用户只说得出"感觉不太行"→ 用 TEST-RUN.md §3 的并排对照法把感觉翻译
   成位置。

### 修复循环

用户判不合格 → 先定位问题层，再修，禁止哪坏改哪的表面缝补：

| 症状 | 问题层 | 回哪修 |
|---|---|---|
| 产出内容本身外行 / 不对味 | craft 层 | 回 Phase 1 补访谈（往往是原则漏了或翻译错了） |
| 流程走岔 / 中间产物漂移 / 该停没停 / 原则忘了 | harness 层 | 回 Phase 2 查适应症表补机制 |
| skill 文本歧义，冷跑 agent 理解偏了 | 表述层 | 直接改文本，改完必须重新冷跑验证 |

每次修完 → 重跑 Phase 3，直到用户判"合格"。**试跑中暴露的每个坑，
写进产出 skill 的 FIELD-NOTES.md**——这是防坑条款唯一合法的出生地
（红线 5）。

**收敛出口**：同一类问题修到第 3 轮仍不合格 → 停止打磨，改做范围收缩
（砍掉最不收敛的环节写进"本 skill 不管什么"，或把它改成交人判断的
硬检查点），带已知限制清单交付。细则见 TEST-RUN.md §4。收窄范围的
可靠 skill，好过全能但不可靠的。

## Phase 4 —— 交付 + 迭代协议

1. **交付物** = skill 包 + 一页"怎么用"说明（业务语言，含：怎么装进自己的
   AI 工具、开场怎么说、中途 AI 停下来问你时意味着什么）。安装说明只写
   确知的事实：认得的工具写具体位置（如 Claude Code 的 skills 目录），
   不认得的工具给万能降级——"把整包文件放进项目里（或直接把 SKILL.md
   发给 AI），说：按这份手册的流程帮我做 XX"——**不许现编具体工具的
   安装步骤**（红线 2 同款纪律：不确定的不编）。
2. **告知迭代协议**（也写进产出 skill 的 FIELD-NOTES.md 头部）：

   > 今后用这个 skill 出了问题，把翻车案例带回来。会走一遍缩短流程：
   > 定位问题层 → 修 → 用你的案例重新试跑。skill 的防坑经验就是这么
   > 攒起来的——翻车不是 skill 失败，是 skill 变强的原料。

3. 交付汇报里如实说明：试跑跑了几轮（用的哪档冷启动）、修了什么、还有
   哪些"待试跑验证"的推演失败模式没有真实案例覆盖；走了收敛出口的，
   附已知限制清单；走了「未验收交付」的，按 TEST-RUN.md §5 显式声明。
