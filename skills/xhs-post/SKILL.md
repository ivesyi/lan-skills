# 小红书图文笔记

把一份内容源变成一篇可以直接复制去发的小红书笔记：文案 + 一组 3:4 卡片图 +
一篇汇总好的飞书文档。

约定两件事：①下文「用户」指操作本 skill 的人（顾问本人或项目负责人），
检查点问的就是这个人；笔记的读者是小红书上的普通刷手机的人。
②本 skill 依赖**同目录的兄弟包** `../xhs-visual-cards/`（卡片图那一摊全归它管），
开工前先确认这个目录在。

## 边界：只出图文，不代发（红线）

这个 skill 的终点是**一篇飞书文档**。它到此为止：

- **不登录小红书**、不操作浏览器、不调任何发布或定时接口、不碰任何
  「一键发布」类工具。
- 用户说「帮我发出去」「顺手发了吧」，也只做到文档，然后告诉他：
  文案在文档里可以整段复制，图在哪个文件夹，去小红书 App 自己发。
  **不要去找发布的办法**。
- 理由（用户原话定的红线）：他要的就是「生成图文即可，放到飞书文档，
  可以一键复制到小红书发布」——最后那一下必须是人点的。发出去的东西
  收不回来，机器不替人担这个责任。

另外不管的：不做数据分析（发完多少赞多少藏）、不做账号运营策略、
不做多平台分发（公众号那条线是另一个 skill 的事）。

## 输入分诊

| 用户给的东西 | 该做的 |
|---|---|
| 一份内容源（诊断报告 / 文章 / 复盘 / 材料链接）+ 说清想让读者看到什么 | 走完整流程（Phase 1 起） |
| 只有内容源，没说这篇要讲什么 | 先反问范围三问（见 Phase 1）。内容源里能讲的点通常有七八个，不锁一个，笔记会写成大杂烩 |
| 只有一个想法/一句话，没有材料 | 反问：这个判断是从哪次真事儿里来的、有没有可引用的细节。本 skill 不替用户凭空编内容，也不拿常识凑一篇 |
| 已经有文案，只要图 | 跳到 Phase 3（卡片规划），但先过一遍 `references/CRAFT.md` §语感，文案不对味先说 |
| 「把这个发到小红书」「帮我发了」 | **停**。按上面的边界节回话：只做到飞书文档，发布你自己点。不要开始找发布路径 |
| 上一篇的返工/追加 | 定位到原工作区（见下），在原文件上改，不另起炉灶；改法见「交付与验收」的反馈速查 |

## 工作区约定

所有内容源与中间产物落在 `.local/xhs-<主题简称>-<日期>/`：

```
.local/xhs-<主题简称>-<日期>/
├── source.md          # 内容源原文/摘录 ★只读，不删
├── copy.md            # 文案 ★标题与正文的唯一出处
├── cards-script.md    # 卡片脚本（封面 + 各内页）
├── cards/             # 出好的 3:4 图（01-cover.png、02-….png …）
└── delivery-doc.md    # 交付文档底稿（贴进飞书用）
```

三条纪律：

1. **`.local/` 不许入 git**（内容源常含真实校名人名，是他人隐私）。
   当前目录没有 `.local/` 约定或它没被 gitignore 时，先确认工作目录不会
   被提交到任何公开仓库，再开工——不确定就问用户放哪。
2. **`source.md` 是只读的、不删**。写卡片脚本时要回 `source.md` 抽具体
   细节（数字、原话、真实例子），**不要只从 `copy.md` 再提炼一层**——
   每转写一层信息就掉一层，末端卡片会变成空话。
3. **`copy.md` 是标题和正文的唯一出处**。同一句标题会同时出现在三处
   （文案区块 / 封面卡片上的字 / 飞书文档标题），改了 `copy.md` 必须顺一遍
   这三处，否则封面写的和正文承诺的对不上。

卡片图默认也存在这个工作区的 `cards/` 里（`../xhs-visual-cards/` 自己的默认
路径是 `assets/<slug>-xhs/cards/`——**以本工作区为准，并保证图片清单里
写的路径和实际文件一致**）。要把图归档进仓库 `assets/` 的，先过一遍
交付前的匿名化扫描。

## 工作流总览

```
Phase 1  接内容源 + 定这篇讲什么（范围三问）
   ▼
Phase 2  写文案（标题候选 3~5 个 / 正文 / 话题标签）
   ▼
Phase 3  规划卡片（封面 + 内页脚本，走 ../xhs-visual-cards）
   ▼
[Checkpoint 对齐]  ← 必须停。一次攒批确认：选哪个标题 / 文案改哪 /
                     卡片脚本对不对 / 用哪条出图通道（要不要花钱）
   ▼
Phase 4  出图  4.1 封面先出一张 → 看一眼（锚点验收，用户可选跳过）
              4.2 其余内页照封面的样子出完
   ▼
Phase 5  汇总飞书文档（文案区块 + 图片清单）
   ▼
[Checkpoint 验收]  ← 必须停。交文档链接给用户验收；发布他自己点
```

为什么只停两处：标题和卡片脚本定错，后面出的图全白出（出图最贵最慢）；
成品验收是用户唯一必须亲自把关的东西。文案的字句不用逐句问——按
`references/CRAFT.md` 写完自查一遍，到检查点一起看。

## 各阶段读文件指南

| 阶段 | 必读（每次都看） | 按需查 |
|---|---|---|
| Phase 1 定范围 | 本文件对应节 | —— |
| Phase 2 写文案 | **`references/CRAFT.md` §语感 + §白话 + §匿名化**；写完过 `references/CHECKLISTS.md` §A | `templates/workfiles.md` |
| Phase 3 规划卡片 | **`../xhs-visual-cards/SKILL.md` 原文 + `../xhs-visual-cards/references/card-guidelines.md` 原文** | `references/CRAFT.md` §卡片（只讲怎么衔接，不转写规范） |
| Phase 4 出图 | 同上（每张图动手前重读提示词骨架）；每张出完过 `references/CHECKLISTS.md` §B | 本文件 §出图通道 |
| Phase 5 成文档 | `templates/delivery-doc.md` | —— |
| 交付前 | **`references/CHECKLISTS.md` §C** | —— |

长会话里原则会淡忘——标了「每次都看」的，动手前重读，不许凭记忆。
尤其卡片规范：**本 skill 不转写 `../xhs-visual-cards/` 的任何内容**，
每次都读它的原文，二手转写丢掉的细节回不来。

## Phase 0 —— 先确认依赖在不在

开工前看一眼 `../xhs-visual-cards/` 这个目录存不存在（同一个 skills 目录下的
兄弟包）。

- 在 → 正常走。
- 不在 → 告诉用户：卡片那一摊的规范在另一个包里，请把它装到同一个
  skills 目录下。**不要凭记忆自己写卡片规范**。
- 用户说「先不管，凑合出」→ 降级：只做文案 + 卡片脚本，图不出，
  在交付说明里写明「卡片规范没对上专门的包，图请人工把关」。

## Phase 1 —— 定这篇讲什么

范围三问，缺一反问：

1. **这篇给谁看**：小红书上刷到的是什么人（同行老师？校长？家长？做内容的？）
   ——读者不同，同一件事的讲法完全不同。
2. **要读者看完做什么/记住什么**：一个动作或一个判断。写不出这一句，
   笔记就会变成流水账。
3. **一篇还是一组**：内容源大的话，长内容可拆 2~5 篇系列，但**不要为了
   凑数量稀释内容**〔`../xhs-visual-cards/` §1 原文〕。

同时定好**匿名化口径**：真实校名、人名、可识别的班级/项目名一律换角色
代称（「一所县域初中」「这所学校的教学副校长」）。小红书是公开平台，
这是红线，见 `references/CRAFT.md` §匿名化。

**内容源拿不到或读不了怎么办**（没权限的链接、打不开的格式、扫描件）：
请用户把关键内容导出成文本或直接粘贴过来，来源记「用户提供」。
拿不到的部分就不写——**不许拿常识补一段看起来像那么回事的内容**，
宁可这篇短一点。

产出：把内容源原文/摘录落 `source.md`，顶部写三行——给谁看 /
要他做什么 / 一篇还是一组。

## Phase 2 —— 写文案

按 `references/CRAFT.md` §语感写，产出落 `copy.md`，三块齐全：

- **标题候选 3~5 个**：每个 ≤20 字、带钩子，**标注各自的钩子是什么**
  （用户要选，得看得出差别）。
- **正文**：口语化分段、第一人称、emoji 节制。**纯文本，不带任何 markdown
  标记**——理由见下。
- **话题标签 5~8 个**〔`../xhs-visual-cards/` §2 原文〕。

**正文必须是纯文本**（不写 `**加粗**`、`#` 标题、`-` 列表符）：小红书正文
不渲染 markdown，那些符号贴过去会原样显示成一堆星号井号。用户要的是
「整段复制直接贴」，带标记就等于让他手工清理一遍。分段靠空行，强调靠
断句和 emoji。

写完过 `references/CHECKLISTS.md` §A，每项写一行结论，fail 先修。

## Phase 3 —— 规划卡片脚本

**动手前读 `../xhs-visual-cards/SKILL.md` 和它的
`references/card-guidelines.md` 原文**，按它的轮播脚本字段逐页写，落
`cards-script.md`。本 skill 只补三条衔接约定：

1. **封面必须兑现选中的那个标题的承诺**——标题说「三个坑」，封面上就得
   看得见那三个坑的具体对象，不能只是一句励志话〔依赖包 §3 原文：
   封面不能只表达泛泛情绪〕。
2. **页数**：封面 1 张 + 内页按文案里能独立扫读的点走，通常 3~7 页
   〔依赖包 §1 的 3–7 个观点〕。凑不满就少出，不注水。
3. **回 `source.md` 抽细节**：每页的「核心画面」要具体可画（具体的物件、
   场景、清单、对比），从原始材料里找真事儿，不要从文案里再抽象一层。

卡片上出现的一切文字同样走匿名化，且**不要出现英文和具体人名**——
这两样在生成图里最容易出岔子（2026-08 公众号线实跑：桌牌上冒出人名和
英文，重生成 3 张）。提示词里写死「无具体人名、无英文」。

## Checkpoint 对齐（**硬节点**）

文案 + 卡片脚本都出来后必须停，一次攒批确认（全白话）：

```
这篇小红书的文案和图的方案都出来了，你定几件事：

1. 标题选哪个：
   A 〔标题〕—— 钩子是〔一句话〕
   B 〔标题〕—— 钩子是〔一句话〕
   C 〔标题〕—— 钩子是〔一句话〕
   （我推荐 A，因为〔理由〕；你说「你定」我就用 A，回头不满意随时换）
2. 正文：〔贴出来〕—— 哪句不对味、哪段太长，直接说。
3. 图打算出 N 张：封面〔一句话画什么〕＋内页〔每页一句话〕。
4. 出图用哪条路子：〔可用通道 1（免费/已有）〕/〔可用通道 2（要花钱，
   大概多少）〕/〔你自己出图，我把脚本给你〕。
   ——要花钱的我不会自己动，你点头我才开始。

定完我开始出图。图出完汇总成一篇飞书文档给你，你自己复制去发。
```

选项类决策的规矩：**必须给带理由的推荐**；用户说「你定」→ 取推荐的第一个，
**明说选了什么、为什么，并给反悔机会**，同时把代定项记下来，验收时优先
复核。

**没对齐前不许出图**（出图慢且可能花钱，返工最贵）。
**无法与用户交互的环境**（被当成一次性任务调用）：不得自行推进，
把待确认项写进 `cards-script.md` 顶部并停在此处交人；**尤其付费通道，
任何情况下都不许自己拍板**。

## Phase 4 —— 出图

### 出图通道（外部依赖，先确认再动手）

出图这一步归 `../xhs-visual-cards/` 管，它写的是用**内置出图能力**每页单独
生成一张完整 3:4 图。但**不是每个环境都有内置出图能力**——动手前先确认
当前环境到底能不能出图，能出就按它的提示词骨架逐张出。不能，按顺序降级：

1. 换本机可用的出图通道：**先把可选的通道列给用户**（哪条免费/已配好、
   哪条要花钱、大概什么价），**付费动作必须用户点头才动**——花钱的事
   机器不替人拍板〔2026-08 公众号线实跑：建付费接入点前是用户拍的板〕。
2. 用户在别的地方自己出图：把 `cards-script.md` 和提示词交给他，出好的
   文件放回 `cards/`，命名 `01-cover.png` `02-….png`。
3. 都不行：只交文案 + 卡片脚本，图留空，**在交付说明里如实写明缺什么、
   为什么**，不要拿别的东西（截图、SVG、拼图）冒充卡片。

不管走哪条：图是 AI 生成的，**交付说明里如实注明**，不替用户瞒。

### 4.1 封面先出一张（锚点）

**先只出封面这一张，出完停下给用户看一眼**。理由：提示词有没有盲区
（文字溢出、排版崩、冒出人名英文），一张图就能暴露，比出完七张再返工便宜。

看什么：过 `references/CHECKLISTS.md` §B。用户点头后再出其余。

用户说「不用看了，全出完一起看」→ 允许跳过，但 §B 的自检照做，
问题攒到成品验收一起说。

### 4.2 其余内页

照封面定下来的样子（同一套视觉逻辑、同样的文字密度）逐张出。
**参考封面的**：整体调性、文字量、标注风格。
**不必对齐的**：画面锚点本身（每页都该有自己的具体画面，机械复制封面
构图会出一套看起来一模一样的废图）。

每张出完过 §B，fail 的当场重出——别攒到最后。

## Phase 5 —— 汇总飞书文档

按 `templates/delivery-doc.md` 写 `delivery-doc.md`，两大块：

- **文案区块**：标题（选定的那个）+ 正文 + 标签，**排成一整块可以整段
  复制的纯文本**，中间不插任何说明文字——用户是全选复制直接贴的，
  夹一句「以下是正文」进去他就得手工删。
- **图片清单区**：每张图一行——文件名 / 本地路径 / 用途（封面还是第几张
  轮播）/ 一句话说明画的是什么。**顺序就是发布时的顺序**。

然后用本机 **lark-cli 的文档创建能力**把它建成飞书文档（具体命令当场查
lark-cli 自己的说明，别凭记忆敲）。图片能上传进文档就上传（用户能直接
在文档里看到图更省事），上传不了就只放路径清单 + 图片文件夹位置——
**如实说明图在本地哪个文件夹**。

**lark-cli 不可用时的降级**：直接把 `delivery-doc.md` 交给用户，他自己贴进
飞书或照着发。交付内容一个字不少，只是少了个链接。

交付前过 `references/CHECKLISTS.md` §C，逐项写结论，fail 先修再交。

## Checkpoint 验收（**硬节点**）

```
小红书这篇做好了：〔飞书文档链接，或 delivery-doc.md 的位置〕

- 标题：〔选定的〕
- 正文：文档里那一整块可以直接全选复制，贴到小红书不用改格式
- 图 N 张：〔文件夹路径〕，顺序按文档里的清单来（第 1 张是封面）
- 图是 AI 生成的
- 〔如有代定项：标题是我按你说的「你定」选的 A，理由〔…〕，要换随时说〕
- 〔如有缺件：第 N 张没出成，原因〔…〕〕

发布你自己来——我不碰小红书。文案哪句不对味、哪张图不行，直接说。
```

按用户的标准验收：这篇发出去像不像那么回事。不合格时**先定位是哪一层**
再改（见下），不做表面缝补。
**无法与用户交互的环境**：同上，停在此处交人。

## 交付与验收：反馈怎么改（先定位层，再改最小切片）

| 用户怎么说 | 是哪一层 | 最小改法 |
|---|---|---|
| 「太硬了 / 像报告 / 不像小红书」 | 文案语感层 | 只改 `copy.md` 正文，重读 `references/CRAFT.md` §语感；图不动。**改完把这条反馈记进 FIELD-NOTES**——语感这层最薄，全靠真实反馈长 |
| 「标题不行 / 没人会点」 | 文案钩子层 | 重出 3 个标题候选给他选；封面若已出且写了旧标题，一并重出封面 |
| 「这张图不行」 | 单页卡片层 | 只重出那一页，脚本里改那一页的核心画面；别整套重来 |
| 「整套图看着乱 / 不统一」 | 卡片规划层 | 回 `cards-script.md` 统一视觉逻辑，重出全部；这时才值得整套重来 |
| 「讲的点不对 / 该讲另一件事」 | 内容范围层 | 回 Phase 1 重定范围三问——这是唯一该推倒重来的情况 |

铁律：不要一句「不太行」就把文案和图全部重做。先问「是哪句/哪张」，
问不出来就拿他认可过的东西并排对照，逐处指认。

## 出了问题怎么办

用这个 skill 翻了车（文案发出去没人看、图崩了、流程卡死、越界了），
把案例记进 [`FIELD-NOTES.md`](FIELD-NOTES.md)：症状 → 定位哪层（内容 /
语感 / 卡片 / 流程）→ 修法 → 用该案例重新试跑验证。翻车不是 skill 失败，
是它变强的原料。**语感层的反馈请务必记**——这一层目前最薄。
